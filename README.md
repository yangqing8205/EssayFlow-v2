# EssayFlow｜高中英语读后续写 AI 评测与修改

EssayFlow 是一个面向高中英语读后续写的 AI 评测与修改产品。它不只是给作文一个分数，而是试图回答一个更具体的问题：

**这篇续写为什么成立、为什么不成立，以及下一步可以从哪里改。**

## 为什么做 EssayFlow

在高中英语读后续写中，常见的高分标准往往是这样的：

> 内容丰富合理，逻辑严密，与原文情境高度融合；词汇和语法结构多样且恰当，表达流畅，仅有极少量不影响理解的错误；衔接自然，全文连贯。

这些标准当然没有错。

但当学生真正坐到考场里，面对一篇需要继续写下去的故事时，问题依然存在：

**“所以，我到底应该怎么写？”**

“内容合理”具体意味着什么？
“与原文高度融合”要融合什么？
“衔接自然”只是把两段连起来吗？
“主题升华”又应该在什么时候发生？

EssayFlow 的切入口，是把这些抽象的评分语言，重新转化为学生能够理解、判断和修改的具体问题。

## 一套关于“故事是否续好”的判断方法

EssayFlow 把一篇续写是否成立，拆成了四个相互关联的问题。

### 01｜矛盾有没有被真正处理？

续写首先要看懂原文留下了什么问题。

这个矛盾是如何产生的？人物为什么陷入现在的处境？续写是否通过新的行动推动了矛盾的发展，并最终给出合理的回应或解决，而不是绕开原文重新讲一个故事？

### 02｜文本有没有真正接上原文？

好的续写不是只在语言上“像原文”，而是要继承原文已经建立的事实、人物关系、情绪状态和情节线索。

人物知道什么、不知道什么，故事发生到哪里，都是后续情节不能随意突破的边界。

### 03｜主题变化是否从故事中自然发生？

所谓“主题升华”并不是在结尾补一句大道理，而是人物经历了某件事之后，对人、关系或自身产生了什么新的理解。

主题应该是情节发展的结果，而不是额外添加的一句话。

### 04｜情节本身是否合理？

人物为什么会做这个决定？事件为什么会这样发生？前一个行动能否自然导致后一个结果？

如果去掉华丽的语言，只看故事本身，它是否仍然成立？

这四个判断共同构成了 EssayFlow 的核心方法论：

**发现矛盾 → 理解原文边界 → 推进人物行动 → 完成主题变化**

它们并不是四个彼此独立的打分项，而是在共同判断一件事：

**这个故事有没有沿着原文已经建立的因果、人物关系和认知变化继续成立。**

在这个基础上，EssayFlow 再去评价语言。

也就是说，它不会一开始就被“词汇高级不高级”“句型丰富不丰富”吸引，而是先判断：

**这个故事有没有被真正续写下去。**

因此，EssayFlow 的评测不是简单地输出一个分数，而是尝试回答一个对学生更有价值的问题：

**这篇续写为什么成立，为什么不成立，以及下一步可以从哪里改。**

## 产品如何把这套方法变成一次评测

EssayFlow 将一次评测组织成完整闭环：

**内容判档 → 语言档内定分 → 文本证据诊断 → 修改复评**

### 内容先决定档位

系统首先围绕四项内容判断整篇故事是否成立：

- **解决矛盾**：是否识别并真正回应原文的核心冲突
- **文本衔接**：是否承接原文事实、人物状态与叙事前提
- **主题表达**：人物的认知变化是否延续或深化原文
- **情节合理性**：人物行动、事件因果和新增情节是否站得住

内容表现首先决定作文所在档位。

### 语言决定档内位置

在内容档位确定之后，系统再通读学生原创语言，判断：

- 准确性
- 清晰度
- 自然度
- 流畅度
- 丰富性
- 语言对叙事的支撑效果

因此，语言表现可以影响一篇作文在档位中的具体位置，但不会因为几个高级词汇或复杂句型，就掩盖故事本身的问题。

### 每一个关键判断都尽量回到文本

EssayFlow 不希望只告诉学生：

> “主题不够深刻。”

它还需要回答：

**是哪一句让我得出这个判断？为什么？下一步应该从哪里修改？**

因此，关键结论需要回到原文或学生续写中的具体文本证据，而不是只输出抽象评价。

### 修改之后，再次验证

反馈最终指向可执行的修改方向。

学生修改之后可以重新提交，让评测形成：

**判断 → 修改 → 再评测**

的闭环。

## 为什么不直接让大模型“评价一下这篇作文”？

通用大模型直接评价续写时，很容易出现几个问题。

### 1. 被语言表面质量吸引

一篇作文可能词汇丰富、句型复杂，但故事本身没有回应原文留下的问题。

因此，EssayFlow 先判断内容，再评价语言。

### 2. 用学生写出的结局反向解释原文

如果模型一开始同时看到原文和学生续写，它可能根据学生已经写出的故事，反过来重新理解原文本来的矛盾与人物状态。

因此，前面的原文分析阶段不会提前接收学生续写。

### 3. 给出听起来合理，却没有证据的评价

“情节不够合理”“主题不够深刻”都很容易生成。

更困难的是回答：

**为什么？依据是哪一句？**

因此，关键判断需要绑定具体文本证据，并经过服务端检查。

### 4. 模型失败时输出一个“看起来没问题”的答案

EssayFlow 不用与本次作文无关的示例结果掩盖真实错误。

如果模型没有配置、结构化输出不符合要求或服务端校验失败，产品会进入明确的异常状态。

## AI 产品可信度设计

### 明确输入边界

系统严格区分：

**原文 / 固定段首句 / 学生原创续写**

固定段首句由题目提供，会保持锁定，不参与学生语言纠错。

### 分阶段理解文本

评测不会一次性把全部内容丢给模型。

整体流程包括：

1. 理解原文既定事实
2. 分析原文线索、人物状态与认知终点
3. 核对学生续写中的事实与行动
4. 完成四项内容判断
5. 在内容档位内定位语言表现
6. 生成证据化诊断与修改建议

### 证据约束

关键评价必须引用原文或学生续写中的对应证据。

服务端会对部分证据与结构进行校验，降低模型生成“听起来合理但文本中并不存在”的判断。

### 结构化输出与失败状态

模型输出需要符合预先定义的数据结构。

如果结构不符合要求，系统只进行有限修复；仍然失败时展示真实异常，不生成伪造结果。

### 示例与真实评测明确区分

脱敏 Demo 与真实模型评测通过独立状态进行区分，避免用户将示例结果误认为自己的作文评测结果。

## 产品流程

1. 粘贴完整题目与学生续写
2. 系统识别原文、固定段首句与学生原创边界
3. 用户确认文本结构
4. 分析原文事实、线索与人物认知终点
5. 核对学生续写中的事实和人物行动
6. 完成四项内容判断并确定档位
7. 在档位内判断语言表现
8. 生成带文本证据的评测报告与修改建议
9. 学生修改后再次评测

## 一个核心设计原则

EssayFlow 的目标不是让 AI 替学生写得更好。

它更希望让学生逐渐看到：

**为什么这里成立，为什么那里不成立。**

评分只是结果。

真正有价值的是把原本藏在教师经验中的判断过程，转化成学生能够理解和使用的反馈。

## 技术实现

技术栈：

**Next.js · React · TypeScript · Tailwind CSS · Zod · Vitest · OpenAI-compatible SDK**

真实评测使用：

`POST /api/v6/evaluate`

服务端以 NDJSON 依次返回不同评测阶段的进度与最终报告。

评分标准由单一 Rubric 文件维护，避免 Prompt 与不同评分版本之间产生不一致。

项目结构主要包括：

- `app/`：页面、路由与 API
- `components/`：界面组件
- `lib/`：数据契约、评测编排、Provider、Prompt 与 Rubric
- `evals/`：自编评测场景
- `tests/`：产品契约与 Workflow 测试
- `docs/`：架构与设计说明

更详细的工程设计见：

`docs/architecture.md`

---

## 隐私与安全边界

- 仓库不包含真实学生姓名、学校等个人信息
- 页面提示用户不要提交姓名、学校等个人信息
- API Key 只存在服务端环境变量中，不进入前端
- `.env*` 默认被 Git 忽略，只保留 `.env.example`
- 当前 MVP 不实现账户与数据库
- 服务端不将完整作文作为历史记录永久保存
